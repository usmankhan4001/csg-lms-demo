# Bug Log — What Broke, Why, and How It Was Found

Chronological record of real bugs found in this project, kept because the *why* is more valuable than the diff: several of these are structural traps (Docker networking, a Next.js version rename, a dual-auth-system split) that will bite again if a new contributor doesn't know about them. See [ARCHITECTURE.md](./ARCHITECTURE.md) for the durable explanation of each trap; this file is the incident history.

Every entry below was confirmed by directly reading the failing code and/or reproducing the failure (container logs, a real browser session, or a test run) — not inferred from a self-report. That discipline exists because an earlier AI session on this project reported fabricated "100% complete" status without the underlying code existing (see `context.md`).

## Foundational fixes (Phase 0)

- **9 of 12 SMS/RevOps routers had no auth dependency at all** — reachable by anyone, logged in or not. `sms_attendance`, `sms_timetable`, `sms_gradebook`, `sms_fees`, `sms_financials`, `sms_hr`, `sms_payroll`, `sms_library`, `sms_revops` only depended on a DB session. Fixed by adding the same `keycloak_auth` dependency already used correctly by `sms_campus.py`.
- **Double auth-gate on 8 SMS routers** (`src/router.py`): after the fix above, 8 routers ended up with *two* incompatible auth dependencies stacked on the same mount, making them unreachable over real HTTP despite passing standalone unit tests. Found while running a real end-to-end test through the frontend, not by the unit suite (which mocks auth). Fixed by keeping only the per-handler Keycloak dependency; added `apps/api/src/tests/routers/test_sms_router_mount_auth.py` to mount the *real* router and catch this class of regression.
- **`test_root_router.py` was broken since the project's first commit** — its stub-module list hadn't kept up with `router.py`. Confirmed via `git checkout` of the very first commit; unrelated to any feature work, just bit-rot in a test's fixture list.

## Getting Docker running for the first time (docker-compose.local.yml)

- **2.4GB build context**: `apps/web/.dockerignore` didn't exist. Added the standard Next.js excludes.
- **`bun.lock` desync**: stale since an earlier commit's `package.json` `overrides` change. Regenerated via a throwaway `oven/bun` container.
- **Self-inflicted `node_modules` corruption**: running `bun install` in a Linux container bind-mounted onto a Windows host corrupted native symlinks. Recovered via `rm -rf node_modules && npm install --legacy-peer-deps`, which surfaced two real (small) type errors from npm's different dependency resolution vs. bun's — fixed directly.
- **Production-build-blocking LaTeX-in-JSX**: raw `$\vec{\tau}$`-style text in `student/courses/[courseId]/lesson/[lessonId]/page.tsx` broke Turbopack's production parser. Never caught by `next dev` (route never visited in dev) — only surfaced on a real `next build`.
- **App crash on non-root container user**: `create_logs_dir()` called bare `os.mkdir("logs")`, which threw `PermissionError` as the container's non-root user. Nothing else reads/writes that directory (confirmed via repo-wide grep) — wrapped in try/except.
- **Port conflicts** on 5433/6380 from an unrelated pre-existing process on the host (confirmed via `netstat`, not killed) — moved to 55433/6390.

## The browser-driven audit round (first real UI testing)

Found by building a throwaway Playwright script and driving the actual running stack through a real browser with a role-matched dev token — none of these were caught by unit tests, `next dev`, or `tsc` in isolation.

- **Every SMS widget showed "You're offline."** Root cause: `lib/api/api-client.ts`, `lib/api/org-features.ts`, and `lib/auth/server.ts` read `process.env.NEXT_PUBLIC_LEARNHOUSE_BACKEND_URL` directly. For client-bundled code, Next.js inlines that at `next build` time — so it baked in whatever (or nothing) was set at build time, permanently, regardless of the container's actual runtime env var. Fixed by switching to `getConfig()`, which reads `window.__RUNTIME_CONFIG__` (populated at container *startup* by `server-wrapper.js`), matching the pattern already used correctly elsewhere in the codebase.
- **Logout was dead**: `<Link href="/auth/logout">` pointed at a route that never existed, 404ing on every page's Next.js prefetch. Fixed by wiring both nav components to the real `useAuth().signOut()`.
- **`/campus-admin` always showed Student nav**, regardless of the logged-in role or token. The role-derivation check tested `pathname.startsWith('/admin')`, but the real route is `/campus-admin` — it never matched — and the check never consulted the actual session at all. Fixed via a real `bucketRealmRole()` mapping read from `useDevSession()`.
- **Wrong default org slug**: `'demo'` (an unverified guess from the original build) vs. the actually-seeded `'default'` — 404s on every load. Fixed after confirming the real value via a direct DB query and the backend's own hardcoded fallback in `src/routers/instance.py`.

## The SSR/Docker-networking bugs (found from a real user report, not self-testing)

A user reported "every screen shows a different bug," pasted a screenshot with React error digest `3754794977`, and — critically — reported it again after the widget-level fixes above shipped, ruling out stale cache. Root cause was structurally different from everything above: these are **server-side** fetches, invisible to any test that pre-seeds a token and drives the app from a browser tab (which is exactly what the audit round above did).

- **Every server-rendered page crashed with "Minified React error #441"** (React's code for "an error occurred in a Server Component render, message hidden in production"). Reproduced by matching the exact digest against the web container's own logs: `TypeError: Unable to connect ... path: 'http://localhost:8000/api/v1/orgs/slug/default', code: 'ConnectionRefused'`. `services/organizations/orgs.ts` (used by ~40 original Learnhouse Server Component pages: login, signup, the entire `/orgs/[slug]` tree) calls `getAPIUrl()`, which server-side resolved to the *browser*-facing backend URL — unreachable from inside the web container's own process, since the API is a separate container. Fixed by adding `LEARNHOUSE_INTERNAL_API_URL` (`http://api:9000`, Docker-internal) and making `services/config/config.ts`'s `deriveAPIUrl()` prefer it when `typeof window === 'undefined'`. Also fixed `lib/auth/server.ts`, which is exclusively server-side and had the identical pattern.
- **Login always said "wrong email or password," even with correct credentials.** Same bug class, in two files the fix above didn't cover because they build their own backend URL instead of going through `deriveAPIUrl()`: `app/api/auth/[...path]/route.ts` (handles login/refresh/logout/signup/mfa/magic-link) and `app/api/auth/token-exchange/route.ts`. The unguarded `fetch()` inside `proxyRequest()` threw on `ConnectionRefused`, Next turned that into a bodyless 500, and the client's `.json()` call on the empty body threw `"Unexpected end of JSON input"` — which the login form's catch-all error handling mislabeled as bad credentials. Fixed the same way (prefer `LEARNHOUSE_INTERNAL_API_URL`).
- **`/auth/login` 404s when visited directly** — not a bug, but easy to mistake for one while debugging the above. The real user-facing URL is `/login`; `proxy.ts` (Next 16's rename of `middleware.ts` — see [ARCHITECTURE.md](./ARCHITECTURE.md)) rewrites it to `/auth/login` internally. Hitting `/auth/login` directly skips that rewrite and falls into the org-scoped catch-all, which has no matching page.

## The dev-token UX gap

- **Clicking any CSG portal link showed "Couldn't load this / Missing Authorization Bearer token header."** Not a code defect in the SMS pages — they correctly required the dev Keycloak JWT described in [ARCHITECTURE.md](./ARCHITECTURE.md#auth-two-systems-not-one). The gap was that obtaining that token required running a Python script and pasting the result into `localStorage` via devtools — undiscoverable by anyone testing through the UI, including a real Learnhouse login. Fixed by adding `/dev-login` (mints the token from the user's real Learnhouse session with one click) and repointing `/home`'s portal links and the role-switcher dropdowns to it instead of the raw portal paths. The role-switchers had a second instance of the same bug: they pushed straight to another role's portal path without re-minting a token for that role, so the *previous* role's token stayed active.
- **`app/dev-login/page.tsx` failed to prerender**: `useSearchParams()` used directly in a page component broke the production build (`useSearchParams() should be wrapped in a suspense boundary`). Caught by reading the actual `bun run build` output, not `tsc` (which doesn't check this). Fixed by moving the hook into a child component wrapped in `<Suspense>`.

## Verification discipline

Every fix above was confirmed by one or more of: reading the actual file after editing, re-running the real backend test suite (not trusting "tests pass" from a subagent's self-report), rebuilding the actual Docker image and driving it with Playwright against a real running container, or matching a live container-log error against a user-reported screenshot's exact digest. This discipline exists because of the fabricated-completion incident referenced at the top of this file — it is the standing operating rule for this project, not a one-off precaution.
